从初始化到每个 cycle

把一场模拟讲清楚：沿着订单、产能、库存和价格，逐步走完真实执行顺序。

先用 3 分钟把项目找回来

我们的研究问题是：在共享产能有限、供应商会暂时断供的环境中，每家制造商固定合作 1、2、3 家供应商，如何改变需求满足率与运营支出？这里的 cycle 是一个离散采购／生产周期，没有校准成一天或一周。

供应商 Supplier报价、接受订单、限量交货

每家价格和产能不同；可能完全停供。

制造商 Manufacturer补货、生产、保留库存

需求固定，库存随周期改变。

合同 Contract连接谁、下多少、交多少

从制造商指向供应商，伙伴固定，分单比例可变。

环境 Environment距离影响运费

平面示意地图，没有道路或运输延迟。

默认有 5 家供应商和 10 家制造商。supplier-count = 2 意味着每家制造商有两个伙伴，共 20 条合同；不是整个网络只剩两家供应商。ABM 的关键在于：多个制造商会争用同一个供应商，个人“选便宜”的决定可能造成系统拥堵，结果由交互产生。

明天先讲这条主线：库存决定补多少 → 报价和已知可用性决定向谁下单 → 新断供与共享产能决定交多少 → 库存加到货决定生产多少 → 本期发货决定下一期报价。

模拟开始前：初始化做了什么

初始化不是 cycle 1。完成 Replay 后 ticks = 0，有初始库存，但累计需求和累计产出仍为 0。

  1. 读取并验证 14 个界面设置，错误时保留已有运行。
  2. 保存设置，清空旧状态，按人数配置地图大小，恢复参数。
  3. 设维护费 50、持有费 1、价格反馈系数 0.20、交互运费系数 3。
  4. 抽供应商基础价 80–120、正常产能为容量基准的 80%–120%；抽制造商固定需求和初始库存 40–80。
  5. 用地图种子放置实体。每家制造商按“基础报价 + 距离×运费系数”选最便宜的 k 家，并固定合同。
  6. 保存初始库存总量，清零账本，重置时钟。首次 Step 才处理 cycle 1。

实际入口：replay-setup → initialize-scenario → create-network。

两个种子：map-seed 管地理位置；scenario-seed 管基础价格、产能、需求、初始库存及供应商／周期的潜在故障抽样。比较 1／2／3 个伙伴时，固定人口、其他参数和两个种子，再 Replay。价格和订单份额是内生结果，可以不同。

每个 cycle：严格按这个顺序

下面 12 步对应 go 中的真实调用顺序。先统一下单，再统一配给，因此普通 ask 的随机执行顺序不会让先处理的制造商优先抢货。参数检查在这些步骤之前。

顺序 / 函数这一步做什么输入 → 输出
01 · recover-suppliers读取上期故障；到期恢复。指定断供首期还不揭示。供应商已知状态 → 本期下单资格
02 · update-supplier-prices可用供应商按上期实际利用率重新报价，再更新合同到货单价。上期利用率 → 本期报价
03 · place-orders先算库存缺口，只向已知可用的已有伙伴按倒数成本分单。期初库存、报价 → 订单
04 · apply-new-outages订单已提交。本期新故障在此生效，不能在本期重新分单。新外部冲击 → 实际可用产能
05 · allocate-supply每家供应商汇总全部客户订单，对所有客户使用同一交付比例。总订单、可用产能 → 配给比例
06 · deliver-orders每条合同的交付等于订单乘配给比例；采购和运输只对实际交付收费。订单、配给比例 → 到货与变动费用
07 · record-supplier-results汇总实际发货，再除正常产能，结果供下一期报价使用。实际发货 → 下期定价依据
08 · update-manufacturer-results期初库存加到货先满足本期需求，剩余留库存；同时计算四类费用。库存、到货 → 生产、期末库存、成本
09 · update-supplier-display先显示停供，再显示订单是否超过产能。这里只更新显示。经济状态 → 节点颜色
10 · update-node-labels供应商显示订单→发货；制造商显示本期满足量/需求。经济状态 → 可读标签
11 · update-network-totals把制造商本期结果求和，再加入累计账本。各制造商结果 → 全网指标
12 · tick（go 末尾）tick 位于最后：已完成周期数加 1，界面图表随之更新。本期全部计算完成 → 下一期
u(t−1) → p(t) → Q(t), order-share(t) → outage(t), fill-ratio(t) → delivery(t) → inventory(t), u(t) → p(t+1)

这里 u 是实际发货除正常产能。箭头表达因果顺序：本期订单不会倒过来修改本期已形成的报价。进入 cycle t 时 ticks = t−1，最后才增加为 t。

跟着一笔订单走完七个 cycle

这是为了讲解而设定的微型案例，不是默认种子的实验结果：2 家供应商、1 家制造商；供应商基础价均 100、正常产能均 30；每条路线运费 20／单位；制造商需求 40、目标库存 40、初始库存 40；合同费每条 50、持有费每单位 1。

S1 在第 2–5 期指定断供，随机风险为 0。第 2 期下单时未知，3、4、5 期已知，6 期恢复。数值由同一套公式计算，并已用 NetLogo 7.0.4 引擎的相同人工设定核对七期结果；显示到 4 位小数，内部保留精度。

七条公式，沿着订单的方向记

规则公式怎么解释
报价pⱼ,t = baseⱼ × (1 + 0.20 × uⱼ,t−1)只对已知可用者更新。u 是实际发货/正常产能，通常在 0–1 之间，所以最高加价 20%。
补货Qᵢ,t = max(0, Dᵢ + Tᵢ − Iᵢ,t−1)D 是生产需求，T 是期末库存目标，I 是期初库存；不是只订 D。
分单cᵢⱼ,t = pⱼ,t + distanceᵢⱼ × freight；sᵢⱼ,t = (1/cᵢⱼ,t) / Σ(1/cᵢₖ,t)分母只含可用的既有伙伴。有订单时成本低者份额大，每个可用伙伴都有正份额。
配给Oⱼ,t = Σᵢ Qᵢ,t sᵢⱼ,t；rⱼ,t = min(1, Cⱼ,t / Oⱼ,t)断供时 r=0；正常无订单时 r=1；否则按共享产能配给。
交货与生产xᵢⱼ,t = Qᵢ,t sᵢⱼ,t rⱼ,t；Pᵢ,t = min(Dᵢ, Iᵢ,t−1 + Σⱼ xᵢⱼ,t)先收到货，再生产；到货和产出可以不同。
库存与缺口Iᵢ,t = Iᵢ,t−1 + Σⱼ xᵢⱼ,t − Pᵢ,t；Uᵢ,t = Dᵢ − Pᵢ,t库存传到下一期。缺口计入历史，但不转成下一期积压。
成本Costᵢ,t = Σⱼ xᵢⱼ,t pⱼ,t + Σⱼ xᵢⱼ,t freightᵢⱼ + 50kᵢ + Iᵢ,t分别为采购、运输、合同维护、库存持有；不含收入或缺货罚金。

为什么希望补货与实际提交仍可能不同？

如果所有既有伙伴都不可用，制造商仍可能想补 80，但实际合同订单为 0。如果有可用伙伴，全部希望补货都会分出去，即使后来因产能不足只交一小部分。需要检查时，用 order-quantity − sum [units-ordered] of my-out-contracts 算出未提交量；精简版不再把它单独存成变量。未提交与提交后未交货仍是两种情况。

共享产能的最小例子

同一供应商产能 100，M1 订 80，M2 订 70。总订单 150，交付比例 100/150 = 2/3，因此分别收到 53.3333 和 46.6667。不是先给 M1 80 再给 M2 20；也不是一人 50。

最容易讲错：断供和价格的时点

时点本期下单时知道吗？本期怎么处理？
指定故障刚开始 / 新随机故障不知道。指定事件虽由实验者设好，制造商没有提前预知。先下单，再设可用产能为 0；已下订单没有当期补救分配。
故障持续的后续期知道。recover-suppliers 保留有效故障。不向它下单，已有合同仍保留；其他既有伙伴承担重新分配的订单。
故障结束后的首期下单前恢复。随机故障还可能再次发生。恢复报价使用上期 0 利用率，因此回到基础价；可以重新接单。
本期发货完成此时才知道本期实际利用率。只写 capacity-utilization，不再修改本期 unit-price。
指定故障 start = 2，duration = 4
有效期：2、3、4、5　｜　第 2 期为 surprise　｜　第 6 期开始前恢复

随机故障的结束期存为 random-outage-through = current-cycle + duration − 1，含结束的那个周期。随机风险 2% 表示符合条件的正常供应商在本周期新发生故障的概率，不表示任意时点只有 2% 的供应商停工。

指定故障与随机故障：旧随机故障可能跨入指定故障窗口，两者取 OR。指定故障或随机故障正在进行时，不再抽新的随机故障。不能简单把两种时长相加，也不能说风险 0 会关闭指定故障。

怎样证明自己理解了模型

先用守恒式检查实现，再用实验判断机制。下面是代码应满足的约束，浮点计算比较时允许小误差。

检查等式或约束为什么有用
订单去向有可用伙伴时 Σ合同订单 = Qᵢ；否则为 0未提交量可用 Qᵢ − Σ合同订单临时计算，不单独存储。
货物守恒Σ供应商发货 = Σ合同交付 = Σ制造商到货排除漏货和重复记货。
库存守恒期初库存 + 到货 = 生产满足量 + 期末库存解释为什么 receipts 不等于 production。
累计库存初始库存 + 累计到货 = 累计生产满足量 + 当前库存检查跨周期状态是否丢失或重复。
需求守恒生产满足量 + 未满足需求 = 固定需求确保缺口没有被当成本期产出。
产能和价格边界发货 ≤ 正常产能；0 ≤ 利用率 ≤ 1；base ≤ 报价 ≤ 1.2×base价格上限只在默认 α=0.20 时为 1.2。
费用守恒总成本 = 采购 + 运输 + 维护 + 持有不能拿总支出低直接解释成效率高。

从每个 cycle 走到实验结论

单个 cycle 是机制更新；一场 500-cycle 模拟是一个 replicate。同一情景下比较 k=1、2、3，再把 30 个情景的配对差做统计。不能把 500 个相邻 cycle 当作 500 个独立样本。

当前模型已补齐六组 BehaviorSpace 定义：风险、产能、库存目标、运费、价格反馈和费用。每种条件使用 30 个情景、每场 500 cycle。已有六组实验报告当时使用 NetLogo 后台引擎加 Java 批量运行器；费用组对已有轨迹重新计价。现在保存的费用组是逐组合重新运行以验证相同账本，不能把这些费用变体算成额外的独立情景。完整参数表和实验 XML 见代码讲解的界面与实验部分。

可以说：在测试条件下，更多伙伴提高平均满足率，也提高每单位满足需求的运营支出。不能说“三家永远最好”或“成本最低就利润最高”。风险为 0 时平均满足率仍分别约为 69.66%、90.79%、99.67%，说明一部分多源采购收益来自缓解集中采购的产能拥堵。

解释边界：这是合成参数、有限时域模型；没有经验校准、收益函数、缺货罚金、相关区域冲击、供应商替换或运输延迟。初始库存免费、终端库存不抵扣。更长期窗口的敏感性检查不能证明平稳性。

Viva 口述：先完整讲一遍

先用中文理清思路，再练下面约 1 分钟出头的简单英文版。按六小段记：比较什么 → 固定伙伴 → 报价下单 → 断供配给 → 库存生产 → 成本与结论；细节等追问时展开。

中文梳理版

我们的模型研究的是，在供应商产能有限且可能暂时断供的条件下，固定选择一家、两家或三家供应商，如何影响制造商的需求满足程度和运营支出。

初始化时，我们生成供应商的基础价格和产能、制造商的固定需求和初始库存，以及决定运费的地理位置。每个制造商按照初始到货单价选定伙伴，之后不再更换合同。

每个周期先处理到期恢复，再用上期实际利用率更新报价。制造商根据需求、目标库存和现有库存算补货量，避开已知断供的伙伴，并按当前到货单价的倒数分单。接着才揭示本期新的断供。供应商汇总所有订单，在产能不足时按比例配给。

供应商先把本期实际利用率存下来影响下一期价格。制造商再用库存加到货满足本期生产，剩余留作库存，不足部分记为丢失需求；同时记录采购、运输、关系维护和库存持有四类支出。最后更新全网累计指标和时钟。

我们固定外部情景比较采购策略。更多伙伴能分散断供风险，也能缓解拥堵，但会增加关系费并可能采购更贵的供给，因此研究的是服务与成本的权衡。

Simple spoken version · 简单口语版

Our model compares using one, two or three suppliers. We look at how much demand we meet and how much we spend.

Buyers choose partners by price plus delivery cost, and keep the same partners.

Each cycle, we check supply and update prices based on how busy suppliers were last cycle. Buyers order based on demand, current stock and target stock. Cheaper available partners get more orders.

New failures happen after ordering. If a supplier cannot fill all orders, it cuts each order by the same percentage.

Buyers use stock and deliveries to meet demand. Extra stock stays. Missed demand is not added to the next cycle.

Costs include buying, delivery, supplier fees and storage. We compare under the same conditions. More suppliers can reduce shortages, but may cost more.

不看答案，回答这 12 个问题

为什么需求 40，订单会是 80？
如果期初库存为 0，目标库存为 40，则 Q=max(0,40+40−0)=80，其中 40 用于当期需求，40 用于补回目标库存。
第 2 期指定断供，为什么这期还有订单发给它？
模型让制造商只知道之前已经发生的断供。第 2 期的新事件在下单后才揭示；这是一项信息与时序假设。
已知故障时会重新选择一家供应商吗？
不会。只是把订单改分到既有合同中的可用伙伴，合同网络不重连。
同一供应商面对多个客户时，谁先拿货？
不分先后。订单全部提交后才汇总并确定统一比例；每条合同按自己的订单量乘这个比例。
为什么利用率不是订单除产能？
价格反馈取决于实际生产。超额订单可能无法交付，订单/产能会超过 1；实际发货/正常产能被限制在 0–1。
下单后发生故障，本期能再把订单转给别人吗？
不能。go 中 place-orders 只在 apply-new-outages 之前执行一次，没有本期二次采购。
已知故障的报价为什么看起来没有更新？
update-supplier-prices 只更新可用供应商；停供者保留旧报价，恢复后按上期 0 发货得到基础价。
没有收到货，为什么仍有成本？
既有合同仍收维护费；如果用完本期需求后仍有库存，也收期末持有费。采购和运输则为 0。
第 5 期缺口 10，第 6 期要不要额外订这 10？
不要。它是 lost demand。第 6 期按当期需求和库存目标重新算 Q；教学例子是 40+40−0=80，不是 90。
为什么固定 seed 并不让两种策略的价格完全一致？
种子固定外部属性与故障抽样。不同合同和订单影响实际利用率，因此内生价格、库存、分单和结果可以不同。
更多供应商的优势全部来自抗断供吗？
不是。即使风险为 0，固定低成本网络也可能把订单集中到少数供应商，增加伙伴还可能缓解产能拥堵。
为什么不能据此宣布最优采购策略？
没有收益、缺货罚金或综合目标，只有服务与运营支出的权衡；结论还依赖合成参数与模型假设。
